# 第一轮 Windows 技术验证

日期：2026-11-10。需求已经用户确认。本轮验证了原生播放端音频采集、原生测试输入框的追加与失效检测，以及本地 CPU / CUDA 识别；尚非可交付的桌面应用。

## 本机和实验配置

- Windows 11 25H2（26200.9711），i5-11400H，16 GiB 内存。
- RTX 3050 Laptop，4 GiB 专用显存，驱动 546.33；未更新系统驱动。
- 项目内安装 Rust 1.99.1 gnullvm、rust-mingw、rustfmt，使用自带 rust-lld，未修改系统 PATH。
- 识别引擎：whisper.cpp v1.8.2 官方 Windows x64 CPU / CUDA 11.8 二进制。
- CUDA 运行库：NVIDIA 官方 libcublas 11.11.3.6，完整下载包 SHA-256 校验通过；引擎日志确认实际使用 CUDA0。
- 多语言 base F16 模型 SHA-256：`60ed5bc3dd14eea856493d334349b405782ddcaf0028d4b5df4088345fba2efe`。
- 测试语音由本机 Microsoft Huihui Desktop 离线合成，识别过程无音频上传。

## 1. 播放端音频采集：基础路径通过

Rust 程序调用 WASAPI loopback，采集默认多媒体播放设备的混合声音，没有打开麦克风，也没有按应用选择声音来源。

- 设备混音格式：48 kHz、双声道、32-bit float。
- 输出：16 kHz、单声道、16-bit PCM WAV。
- 原始合成语音：25.875 秒；采集文件：26.460 秒，包含边缘静音。
- 对齐后覆盖了原始样本的完整 25.875 秒，波形归一化相关系数约 0.988；采集音频成功用于后续识别。
- 观察到 3 次 discontinuity 标记，原因和实际缺帧情况尚未进一步定位，正式采集模块仍需事件驱动、独立采集线程及长时间压力验证。

只测了当前默认多媒体播放端点。不同耳机、默认通信设备与多媒体设备分离、应用单独路由以及中途切换设备的行为仍待验证。

## 2. 保存目标与追加：原生控件路径通过

在自建的隐藏原生测试窗口中创建两个输入框，保存第一个控件的 UI Automation 引用，然后模拟采集期间用户新增编辑：

- 写入前读取最新内容，追加中文、英文和数字；新旧内容均保留。
- 写后读取全文，确认与预期一致。
- 旁边的输入框内容保持不变。
- 销毁原目标后，继续追加返回失败，可交由上层备用文本框处理。
- 程序未注入 Enter 或调用任何发送动作。

本次直接以测试控件句柄获取 UIA 引用，未测试全局快捷键获取实际用户焦点，也未操作 Codex、浏览器插件或其他现有应用。正式备用文本框和无 ValuePattern 控件的适配尚未实现。该结果证明基础路径可行，不构成任意输入框兼容性保证。

## 3. 本地识别：CPU 和 CUDA 均通过

同一份 26.460 秒采集文件，6 CPU 线程，默认 5 beams / best of 5，中文识别，不显示时间戳。下表为整个 CLI 进程的墙钟时间，包含模型加载；每次均启动新进程。

| 后端 | 实测进程耗时 | 备注 |
| --- | ---: | --- |
| CPU 第一次 | 2.764 秒 | 强制关闭 GPU |
| CPU 第二次 | 2.729 秒 | 相同模型和音频 |
| CUDA 第一次 | 12.804 秒 | 本机首次运行该 CUDA 引擎，启动开销明显 |
| CUDA 第二次 | 1.217 秒 | 日志确认模型使用 CUDA0 |
| CUDA 第三次 | 1.173 秒 | 日志确认模型使用 CUDA0 |
| CUDA 第四次 | 1.243 秒 | 加强基准脚本的后端确认后再次通过 |

这是合成语音单样本基准，测量次数少；不代表真实会议准确率，也不等于最终工具停止采集后的整条操作延迟。首次 CUDA 明显较慢，需要在正式工具中评估预加载、预热及可用状态提示。

识别结果基本覆盖测试文本，但产生了繁体中文，并把“本机”识别成“本季”。模型选择、解码参数、简体中文输出以及真实中英混合发言仍需验证。该基准模型仅用于确定本地推理可运行，尚未确定产品最终模型。
