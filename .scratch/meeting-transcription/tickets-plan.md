# 耳机音频转写：任务拆分与发布记录

来源：[规格 Issue #1](https://github.com/xiaolin624/listen/issues/1)。拆分依据为父规格完整正文及评论；拆分时父规格没有评论。

状态：用户已确认任务粒度和阻塞关系；10 个子 Issue 已全部发布并标记 ready-for-agent，已核对 10 条原生父子关系和 14 条原生阻塞关系。本轮仅处理文档与 Issue，没有修改代码。

## 拆分原则

每项任务都从真实使用流程进入，并交付可演示或可验收的行为。现有仓库只有技术验证程序；第一项任务建立最小完整闭环，后续任务逐步增加回填、长时间使用、恢复和性能能力。当前没有需要先执行的生产代码重构。

T1–T10 是任务标识，与实际 GitHub Issue 编号的对应关系见下表。每项已单独成为 Issue #1 的子 Issue，阻塞项已转换为真实 Issue 的原生依赖。

父规格提供需求上下文，不作为实施任务的阻塞项。父 Issue 的标题、正文、状态、标签和评论保持不变。

## 已确认的任务

1. **T1：快捷键采集耳机音频并得到可复制的本地转写。** 阻塞项：无。交付可运行的最小闭环：后台开始/停止、真实播放端采集、本地识别、备用文本框和必要状态。
2. **T2：向预先选定的原生输入框追加转写文本。** 阻塞项：T1。交付选定目标、切窗后仍回填原框、保留最新原文和手动发送的完整流程。
3. **T3：通用桌面及网页编辑区的自动回填。** 阻塞项：T2。交付工具自行适配编辑区的能力，并实际验证 Codex 桌面端和网页/插件编辑区；无法可靠写入时回退。
4. **T4：写入异常、超长结果和重复操作下保全结果。** 阻塞项：T2。交付目标失效、只读、容量不足、写入未确认及重复停止等情况下不误投、不重复追加、结果可复制的流程。
5. **T5：长时间后台分段转写与完整停止收尾。** 阻塞项：T1。交付无产品预设时长上限的持续处理、跨段完整结果、有界音频缓存及积压反馈。
6. **T6：识别失败后重试及临时音频生命周期。** 阻塞项：T1。交付不重放原发言即可本地重试、成功清理、失败保留和用户清理的完整流程。
7. **T7：耳机播放路由变化与采集中断反馈。** 阻塞项：T1。交付设备变化和播放路由差异下捕获正确耳机音频、或明确中断并保留结果的流程。
8. **T8：普通话、中英混合及无语音场景的本地识别质量。** 阻塞项：T1。交付经过已知音频对照选择的本地识别方案，接入实际流程，并处理静音和非语音结果。
9. **T9：硬件加速、准备状态与端到端延迟优化。** 阻塞项：T5、T8。交付模型复用/准备和本机加速策略，以一致的质量条件实测首次及后续使用体验。
10. **T10：Windows 可运行交付包与整体验收。** 阻塞项：T3、T4、T6、T7、T9。交付能按说明启动并完成全部使用流程的应用包，以及覆盖父规格的验收证据。

## 为什么是这些阻塞关系

- T1 提供所有后续任务需要的可运行应用、采集到输出的控制入口和备用文本框。
- T2 需要 T1 的真实转写结果和交付入口；T3、T4 分别在它之上扩展编辑区适配与失败行为。
- T3 的编辑区适配与 T4 的异常流程可以独立验收；二者均承接已有的正常追加和备用输出约定。
- T5、T6、T7、T8 均可使用 T1 的备用文本框完成端到端验收，因此不必等待自动回填任务。
- T9 需要 T5 的持续处理路径，以及 T8 的识别质量基线，才能评价长时间使用和不降低质量条件下的性能。
- T10 是整体交付验收；它直接等待各条分支的末端。T1、T2、T5、T8 已通过传递依赖包含在内，无需重复添加阻塞边。

## 验收方式

沿用已确认的单一主要业务测试入口：开始一次采集，到停止、转写和结果交付完成。可控的外部依赖用于重复故障和事件顺序；实际设备、编辑区和本地模型补充集成验证。每项任务同时交付它引入行为的验证证据。

短音频、60 分钟音频及本机性能数字都是验证样例或基准，不是产品时长上限、准确率承诺或固定延迟 SLA。T1 的最小演示不表示长时间使用和所有编辑区已经验证。
