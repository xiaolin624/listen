# 耳机音频转写工具规格

状态：需求和测试边界均已由用户确认。

## Problem Statement

用户在 Windows 电脑上通过耳机参加远程会议、聊天或收听其他应用的语音，希望把听到的发言完整转成文字，再交给大模型或 agent 使用。耳机中的声音不适合依靠麦克风再次收音；手工复述、整理和复制会打断当前工作。

用户需要按需采集一段声音，在结束时将转写文本追加到自己预先选定的目标输入框，由自己检查并发送。工具应在后台工作，不持续展示字幕，也不要求用户按会议软件或输入框类型分类操作。

## Solution

提供 Windows 后台工具，以全局快捷键控制一次采集的开始和停止。

标准流程：用户点击或双击目标输入框 → 按快捷键开始采集并锁定该目标 → 采集耳机音频，在本机后台处理 → 再按快捷键停止 → 将完整转写文本追加到原目标输入框 → 用户手动发送。

耳机音频指当前耳机正在播放的全部声音，可以来自一个或多个应用。工具转写其中的语音，不要求用户选择声音来源应用，也不主动开启麦克风。

用户切换窗口不改变本次已选目标。没有有效目标输入框，或无法可靠完成自动追加时，使用备用文本框展示当前转写文本，供用户复制粘贴。

识别以普通话及夹杂的英文单词、技术词为首要场景，全部在本机进行。单次采集不设置固定的分钟数上限；通过持续处理和受控缓存支持长时间使用。优先追求低延迟和较低资源占用，以 Rust 为优先实现选择，并根据本机测试选择本地识别引擎和加速方式。

## User Stories

1. 作为 Windows 用户，我希望工具在后台常驻，以便在会议或聊天期间随时开始采集。
2. 作为佩戴耳机的用户，我希望直接获取耳机音频中的语音，以便正常使用耳机时也能转写。
3. 作为用户，我希望采集范围覆盖当前耳机播放的全部音频，以便不同应用及多个应用同时播放时使用同一套操作。
4. 作为用户，我希望无需选择腾讯会议、飞书或其他声音来源应用，以便工具适用于通用播放场景。
5. 作为用户，我希望工具不主动采集我的麦克风声音，以便首先解决耳机播放内容的转写需求。
6. 作为用户，我希望先选定目标输入框，再开始采集，以便明确本次文字的输出位置。
7. 作为用户，我希望一次快捷键即可开始采集，以便鼠标可以继续留在其他应用中。
8. 作为用户，我希望工具在开始时记住本次目标输入框，以便中途切换窗口后仍能向原目标输出。
9. 作为用户，我希望工具适配自己选定的输入框，以便使用时无需理解桌面应用、网页插件或控件类型的区别。
10. 作为用户，我希望再次按快捷键即可停止采集，以便按实际发言的边界获取文字。
11. 作为用户，我希望任意长度的单次采集都不受产品预设分钟数限制，以便短句和长时间讨论都能使用。
12. 作为用户，我希望采集期间不持续弹出转写字幕，以便保持当前会议和输入框的工作状态。
13. 作为用户，我希望能了解工具是否已经开始、正在处理或发生错误，以便确认操作生效。
14. 作为用户，我希望识别在本机完成，以便正常转写不依赖云端语音识别服务。
15. 作为用户，我希望模型准备好后可以断网使用，以便网络状况不影响已具备条件的本地识别。
16. 作为用户，我希望普通话及夹杂的英文单词、技术词得到识别，以便保留实际讨论内容。
17. 作为用户，我希望得到保留发言内容的转写文本，以便自行决定如何交给大模型或 agent 处理。
18. 作为用户，我希望停止后尽快获得结果，以便继续当前对话。
19. 作为用户，我希望长时间采集的处理过程不无界积累音频内存，以便会议能保持正常运行。
20. 作为用户，我希望文字追加到目标输入框已有内容的末尾，以便原来的草稿得到保留。
21. 作为用户，我希望采集期间在目标输入框中新写入的内容也得到保留，以便不用停止自己的编辑工作。
22. 作为用户，我希望追加只作用于本次选定的目标输入框，以便其他窗口或输入框不会被意外修改。
23. 作为用户，我希望由自己检查并手动发送文字，以便控制发给大模型或 agent 的最终内容。
24. 作为用户，我希望重复的停止操作不会重复追加同一份文字，以便避免重复内容。
25. 作为用户，我希望没有有效目标输入框时仍能得到可复制的转写文本，以便手动粘贴。
26. 作为用户，我希望目标关闭、变成只读或无法写入时显示备用文本框，以便转写结果不会丢失。
27. 作为用户，我希望工具无法确认写入结果时保留完整转写文本，以便我可以检查目标内容后自行处理。
28. 作为用户，我希望备用文本框保留当前结果供查看和复制，以便无需重复播放原来的发言。
29. 作为用户，我希望没有有效语音时不会向输入框追加凭空生成的内容，以便结果符合实际收听内容。
30. 作为用户，我希望模型未准备好或识别失败时有明确反馈，以便知道本次操作是否完成。
31. 作为用户，我希望识别失败后能利用本次保留的临时音频重试，以便无需重新让对方发言。
32. 作为用户，我希望播放设备变化或采集中断时有明确反馈，以便不会误以为所有音频仍在正常采集。
33. 作为用户，我希望转写成功后的临时音频被清理，以便避免不必要的音频积累。
34. 作为用户，我希望工具不自动建立会议历史，以便第一版保持简单并只处理当前结果。
35. 作为用户，我希望本地硬件加速能经过实测选择，以便真正降低使用过程中的等待。
36. 作为用户，我希望模型首次准备及后续识别的等待能够被正确区分，以便了解工具什么时候已经可用。
37. 作为用户，我希望资源不足或出现积压时获得明确反馈，以便不会在没有提示的情况下丢失发言。

## Implementation Decisions

### 已确定的产品约束

- 第一版运行于 Windows；已有本机验证环境为 Windows 11。其他 Windows 版本的支持范围以实际验证为准。
- 使用耳机实际播放路径的设备级混合音频，不以会议软件 SDK、按应用筛选或应用白名单作为核心采集范围。
- 耳机播放的语音均属于采集范围；来自本机播放的本人录音或回声也属于该范围。工具不另行开启麦克风。
- 用户先通过点击或双击明确选择输入框，再用快捷键开始；工具须在改变焦点前记住本次目标。中途焦点变化不自动改变目标。
- 自动写入面向通用可编辑输入框，具体能力由工具适配。Codex 桌面端、浏览器及插件编辑区属于代表性验证场景，不构成要求用户选择的应用清单。
- 在停止后的最终输出阶段，将文本追加到目标当时的最新内容末尾，保留已有内容及采集期间新增的编辑；不能用开始时的内容快照覆盖最新草稿。
- 输出内容是转写文本。发送操作始终由用户完成；文字中的换行也不得造成自动发送。
- 无目标、目标失效、只读、禁用、容量不足、缺少可用写入方式，或写后结果无法确认时，保留完整转写文本并进入备用文本框。不得改向其他看似相同的控件，也不得静默截断超长结果。
- 写入结果不确定时不盲目重试。若存在部分写入的可能，明确提示用户先检查目标内容，再决定是否复制粘贴，避免重复追加。
- 采集和识别过程不持续展示字幕。工具提供就绪、采集中、处理中及错误等必要状态；正常开始采集不先抢走目标输入框焦点。
- 单次采集没有固定时长上限。实际内存、显存、磁盘等资源不足时明确反馈，并保留已采集内容或可恢复结果；不能将静默丢音当作正常完成。
- 第一版保留当前转写结果，不自动建立历史归档。临时音频成功转写后清理；识别失败时保留本次临时音频供重试，并提供明确的重试或清理处理。

### 模块职责与交互约束

- 应用控制负责快捷键、当前采集状态、目标绑定、停止收尾及结果交付，使一次采集的音频、目标和结果保持对应。
- 音频采集负责播放设备的混合音频获取、状态变化反馈和受控的数据交付；识别处理不能阻塞设备取音。
- 本地识别负责持续处理已采集音频、保留时序和边界内容，并在停止后收尾。长录音不能全部积压到停止时再一次性加载进内存。
- 音频缓存和识别任务队列须受控。分段时处理跨段词句、顺序和重叠，避免边界遗漏、重复或乱序。
- 目标输出负责验证已绑定目标、读取最新内容、追加和确认结果；备用文本框承接没有可靠目标或写入未确认的结果。
- 临时数据管理负责成功清理、失败保留及重试结果的生命周期；临时文件布局不属于对外契约。
- 重复快捷键或停止事件不得导致同一结果多次交付。不同采集的目标与结果不得混淆；处理中遇到新操作时须给出明确状态，避免静默丢弃。
- 播放设备切换、默认通信设备与默认多媒体设备不同、应用单独路由等情况须在实际耳机路径上验证。无法确定或继续捕获正确设备时明确反馈中断，保留已有内容。
- 模型未准备好或本地后端不可用时明确反馈，不能显示并未实际发生的正常采集或识别状态。任何本地失败均不得静默改用云端识别。

### 技术选择的当前状态

- Rust 是优先实现选择，性能判断以本机端到端测量为依据；具体 GUI 框架尚未确定。
- 设备级 WASAPI loopback 和 UI Automation 原生控件写入已有基础实验依据，正式实现仍需完成焦点获取、实际控件适配和故障处理。
- whisper.cpp 与多语言 base 模型是已验证的本地推理候选组合。最终引擎、版本、模型、解码参数和中文输出规范化方案尚未定型，不能将实验模型直接认定为最终质量选择。
- 本机 CUDA 后续运行快于 CPU，但首次启动明显较慢。正式实现需评估模型复用、预加载及预热，同时验证其资源占用和首次使用体验。
- 尚未约定最大等待秒数、准确率百分比或固定内存数值。本规格保留“尽量高性能”的目标，以可复核测量指导优化，不将实验耗时改写成已承诺的产品 SLA。

## Testing Decisions

### 主要测试边界：一次完整的采集及输出

以“一次开始采集，到停止、转写和结果交付完成”的完整流程作为唯一主要业务测试入口。测试通过与正式快捷键相同的应用控制入口驱动开始和停止，观察采集状态、目标绑定、最终文本、备用显示和临时音频生命周期。

音频设备、识别引擎、目标编辑区等外部依赖可以使用可控替身，使模型文本、故障和事件顺序可重复；这些是同一流程的环境替换，不为每个内部函数另设业务测试入口。真实 Windows 设备、实际编辑器和本地引擎则在同一条使用路径上完成集成验证。

### 什么是有效测试

- 检查用户能观察到的行为及结果，不断言内部函数调用次数、线程数量、临时文件命名或具体库的私有结构。
- 使用确定的转写结果检验目标绑定、追加、重复控制和错误回退，避免用模型随机差异判断应用逻辑是否正确。
- 对真实识别单独使用已知文本的音频，报告错字、遗漏、英文词识别及输出格式；不把仅产生了非空文字视为准确率通过。
- 对所有自动输出路径检查未发生发送动作、未修改非目标输入框、未丢失目标原文；无法确认时观察是否正确保留结果并回退。
- 每个测试覆盖正常结果或一个明确的失败条件，优先从完整流程进入；确需隔离硬件故障时，也围绕可观察行为设计集成测试。

### 覆盖的职责

通过同一主要边界覆盖应用控制、音频交付与分段、本地识别结果收尾、目标输出、备用文本框以及临时数据生命周期。对原生设备路由、真实输入框能力和本地推理后端追加集成测试与性能测量。

### 关键验收场景

| 场景 | 外部操作或条件 | 必须观察到的结果 |
| --- | --- | --- |
| 正常完整流程 | 选择输入框、开始、提供语音、停止 | 向原目标追加一份完整结果，由用户手动发送 |
| 混合播放来源 | 不同应用向同一耳机播放已知语音 | 无需选择来源应用，相关语音均进入采集范围 |
| 不采集麦克风 | 仅麦克风有声音，耳机没有相应语音 | 工具未主动读取麦克风并转写其输入 |
| 切换窗口 | 开始后把焦点切到另一个应用或输入框 | 输出仍绑定原目标，其他输入框不变 |
| 原文与新增编辑 | 目标原有草稿，采集期间继续编辑 | 停止时保留最新草稿，在末尾追加转写文本 |
| 通用编辑区 | 原生控件、Codex 桌面端、网页及插件编辑区 | 工具自行适配；可确认写入则追加，否则提供完整结果供复制 |
| 无有效目标 | 开始时没有可绑定的编辑区 | 完成转写后显示备用文本框，不误选其他窗口 |
| 目标失效 | 目标关闭、重建、只读或禁用 | 不改写替代目标，当前结果进入备用文本框 |
| 写入未确认 | 写后内容不符、超时或可能部分写入 | 保留完整结果并提示检查，不自动重试造成重复 |
| 目标容量限制 | 长时间采集的结果超出目标可接收字数 | 不将截断结果当作成功，备用文本框保留完整转写文本 |
| 手动发送 | 转写包含多行、中英文和符号 | 内容完整追加，任何换行或快捷键均未触发发送 |
| 重复控制事件 | 按住快捷键、重复停止、处理中收到操作 | 状态可解释，同一段结果不重复输出、不混入其他采集 |
| 静音与非语音 | 只有静音、音乐或提示音，没有有效语音 | 不向目标追加凭空生成的发言，给出恰当状态 |
| 分段边界 | 词句跨越识别分段，短于一段时即停止 | 最后不足一段的内容仍收尾，输出顺序正确且边界不重复、不遗漏 |
| 识别失败及重试 | 模型失败或后端不可用 | 明确失败，临时音频可用于本地重试，不外发到云端 |
| 成功清理 | 得到有效转写结果，包括走备用文本框的情况 | 临时音频按成功规则清理，当前结果仍可查看和复制，不生成历史归档 |
| 设备变化 | 播放路由改变、设备断开或默认设备分离 | 捕获正确耳机路径，或明确反馈中断并保留已有内容，不静默采集错误设备 |
| 长时间及积压 | 连续至少 60 分钟的已知音频，并模拟识别变慢 | 无产品预设时长截断；音频缓存和队列内存受控，积压可见，资源耗尽明确反馈 |
| 模型首次准备 | 首次运行、模型缺失或首次 CUDA 使用 | 准备状态明确，与可正常采集及识别的状态正确区分 |
| 断网使用 | 本地模型已准备后断开网络 | 本地采集及识别仍可进行，不依赖云端识别请求 |

其中 60 分钟是长时间验证样例，不是产品允许采集的最长时间。尚未规定识别文字的零错误保证或对所有控件无条件自动写入的承诺；真实模型质量与平台限制需如实报告。

### 性能与资源测量

- 在已记录的本机配置上使用同一音频、同一模型和同一解码设置比较后端，分别记录首次使用及后续运行。
- 记录从停止操作到结果出现在原目标或备用文本框的端到端耗时；识别进程基准不能代替该指标。
- 记录长时间采集的音频缓存、任务积压、进程内存、GPU 使用与显存，以及同时开会时的流畅度表现。
- 长时间场景检验音频缓冲和任务队列不按总音频长度无界增长，不能用不断积累完整音频的方式达到表面上的不限时。
- 保持对照的模型和质量条件，避免只换更差的识别结果来宣称性能提升。

### 已有实验与测试先例

- 当前仓库只有技术验证程序，没有正式桌面应用、会话控制模块或完整业务测试套件，因此主要业务测试入口需要在正式实现中建立。
- 已有原生测试控件实验验证了保存 UIA 引用、读取最新内容后追加中文和英文、原文保留、旁边控件不变及目标销毁后返回失败。
- 已有设备级 loopback 实验和固定合成语音，可作为音频路径集成测试的起点。
- 已有本地 CPU / CUDA 识别基准工具，可延续其固定模型和记录整次运行耗时的方式；这些工具不是正式产品的最终接口。
- 现有实验未验证实际全局快捷键获取焦点、Codex 或网页控件回填、正式备用文本框和长时间后台分段识别；相应场景不能列为已经通过。

## Out of Scope

- macOS、Linux、手机端及跨设备音频采集。
- 主动采集麦克风、将本人麦克风声音混入转写、按参会人分离音轨或识别说话人身份。
- 会议软件专属插件、按来源应用筛选声音，以及要求用户选择输入框所属应用类型的操作流程。
- 实时字幕、自动总结、翻译、会议纪要提炼和内容改写。
- 自动发送消息、调用大模型或 agent 的 API、替用户执行转写内容。
- 自动建立会议历史、长期音频归档、云端同步、账户和团队管理功能。
- 在本规格中确定尚未测定的最终识别模型、GUI 框架或数值性能 SLA。
- 无条件保证所有平台限制下的输入框都能自动写入，或保证任意会议音频逐字零错误。

## Further Notes

### 已确认的名词

- 耳机音频：用户所用耳机正在播放的全部声音，可以包含多个应用的声音。
- 转写文本：由耳机音频中的语音转换得到的文字，保留发言内容。
- 目标输入框：用户明确选定、希望接收转写文本的其他应用输入框。
- 备用文本框：工具自身提供、用于查看及复制当前转写文本的文本框。

### 已有本机测量

测试机器为 Windows 11、i5-11400H、16 GiB 内存及 RTX 3050 Laptop 4 GiB 显存；NVIDIA 驱动 546.33。

实验使用 whisper.cpp v1.8.2、多语言 base F16 模型及同一份 26.460 秒的离线合成中文采集文件。模型文件 SHA-256 为 60ed5bc3dd14eea856493d334349b405782ddcaf0028d4b5df4088345fba2efe。

采集实验仅验证当前默认多媒体播放端点，观察到 3 次 discontinuity 标记，尚未进一步定位实际缺帧情况。输入框实验使用自建原生控件并通过句柄获取 UIA 引用，不能推导为真实焦点锁定或任意输入框回填已经完成。

### 实施时仍需验证的事项

- 通用输入框在切换窗口、控件重建及并发编辑时的定位、追加和写后确认能力；无法确认时回退。
- 实际耳机、通信与多媒体播放设备分离、应用路由和设备切换的覆盖。
- 长时间分段识别的边界质量、收尾延迟、受控缓存和积压处理。
- 首次准备、预加载与加速策略，以及真实会议中的普通话和中英混合识别质量。
- 默认快捷键的选择和冲突处理等实施细节，不重新限制已确认的通用声音及输入框范围。
